🔦 The Cold Open

Open sales_ledger.csv and check its size on disk: 41,719 bytes. Now save the exact same 1,200 rows as a Parquet file and check again: 18,236 bytes. The CSV is 2.3× larger — and that gap only widens at real scale.

But size is the smallest part of this story. Every time a tool opens a CSV, it re-guesses the schema from scratch. A Parquet file carries its own schema stamped inside it — column names, types, everything — before a single data row is touched.

Session 2 is about what happens when you stop treating the file as a bag of text and start treating it as a versioned, self-describing table.

01
CSV vs Parquet

"A CSV is just text. A Parquet file is a self-describing table with its schema embedded — nobody re-guesses anything."

The difference shows up immediately when you read dtypes. pandas infers them from scratch every time it opens a CSV. pyarrow reads Parquet's schema from the file's own footer — in microseconds, before touching a data row.

import pandas as pd
import pyarrow.parquet as pq

# CSV — pandas re-infers types by scanning every row
print(pd.read_csv("sales_ledger.csv").dtypes)

# Parquet — schema is stored in the file footer
print(pq.read_table("sales_ledger.parquet").schema)
OUTPUT
CSV dtypes: order_id int64 · region object · product object · revenue float64 Parquet schema: order_id: int64 · region: large_string · revenue: double
💼
Interview signal

A data engineering JD that lists "Parquet" is asking for comfort with columnar, self-describing file formats. Converting a CSV-based pipeline to Parquet is one of the most common first wins a new hire delivers on a legacy data stack — it's the right answer when someone asks "how would you speed up ingestion?"

❓
FAQ — "If Parquet is better in every way, why does CSV still exist?"

CSV is human-readable in any text editor and every tool on the planet can open one. That universality is a real feature for small handoffs and quick inspection. Parquet trades that away for schema, compression, and columnar layout — the right trade the moment a pipeline runs more than once.

02
Apache Arrow — Deep Dive

"Apache Arrow is the in-memory version of what Parquet is on disk — the same columnar idea, just living in RAM instead of a file."

This is why Session 1's Polars ↔ DuckDB zero-copy handoff worked with no conversion code. Both tools use Arrow as their native in-memory format — the data never leaves columnar layout at all.

Compute Without Leaving Arrow

You can filter and aggregate in Arrow directly, without converting to pandas or Polars — useful when data is about to be handed to another Arrow-native tool and you don't want even one intermediate copy.

import pyarrow.parquet as pq
import pyarrow.compute as pc

t = pq.read_table("sales_ledger.parquet")
mask     = pc.greater(t["revenue"], 500)
filtered = t.filter(mask)
print(filtered.num_rows, "of", t.num_rows, "rows")
OUTPUT
574 of 1200 rows
🔗
The quiet standard behind everything in this course

Polars, DuckDB, Parquet, and the Iceberg table format coming up next all read and write the exact same in-memory column layout. That one shared agreement is why none of Session 1's demos needed a single explicit .to_pandas() or conversion function.

03
The Iceberg Idea

"A single Parquet file is a finished snapshot. A table format turns a folder of Parquet files into something that behaves like a real table — with history."

When new rows arrive, there's no clean way to add them to a Parquet file, fix a mistake, or see what the data looked like yesterday — not without juggling filenames by hand. A table format is the missing layer.

❓
FAQ — "Isn't a table format just a database?"

Not quite. A database owns its storage and query engine end to end. Iceberg only owns the bookkeeping: which Parquet files belong to the table, what the schema is, and what every past version looked like. Any engine that understands that bookkeeping — DuckDB, Spark, Polars, or plain Python — can read or write the same table without ever going through a database server.

💻
No cloud required

pyiceberg is a pure-Python library. Its SqlCatalog stores bookkeeping in a plain local SQLite file. Everything in today's lab runs on a laptop with no network connection at all.

04
Building a Local Iceberg Table

"Every step here is exactly what a production Iceberg table does — just with a SQLite file instead of a catalog server."

  • Create a local catalog

    One call — SqlCatalog writes a SQLite file into the iceberg_warehouse folder. That's the entire "database" for today.

  • Create the table and append data

    Schema comes from the Arrow buffer (pa.Table.from_pandas(df, preserve_index=False)). First append → first snapshot → 1,200 rows.

  • Append again and inspect history

    Second append creates a second snapshot. Neither one rewrites the other's Parquet file. That's the atomic-write guarantee.

  • Evolve the schema — add a column

    One call. Existing rows get null for the new column. Zero rewriting. That's schema evolution.

  • Time travel to the first snapshot

    Pass a snapshot_id to .scan(). You get the table as it was before the second append — no restore, no backup.

Key code patterns

import os, pandas as pd, pyarrow as pa
from pyiceberg.catalog.sql import SqlCatalog

# Step 1 — catalog
warehouse_path = os.path.abspath("iceberg_warehouse")
catalog = SqlCatalog("local",
    uri=f"sqlite:///{warehouse_path}/catalog.db",
    warehouse=f"file://{warehouse_path}")
catalog.create_namespace("sales")

# Step 2 — table + first append
df         = pd.read_csv("sales_ledger.csv")
arrow_tbl  = pa.Table.from_pandas(df, preserve_index=False)
table      = catalog.create_table("sales.orders", schema=arrow_tbl.schema)
table.append(arrow_tbl)   # → 1 snapshot, 1,200 rows

# Step 3 — second append → 2 snapshots
df2 = df.sample(200, random_state=1).reset_index(drop=True)
table.append(pa.Table.from_pandas(df2, preserve_index=False))
for snap in table.history(): print(snap)
# → snapshot_id=84493…  snapshot_id=77055…

# Step 4 — schema evolution (no rewrite)
from pyiceberg.types import DoubleType
with table.update_schema() as update:
    update.add_column("discount_pct", DoubleType())
# existing rows → null in discount_pct; nothing rewritten

# Step 5 — time travel
first_snap = table.history()[0].snapshot_id
print(len(table.scan(snapshot_id=first_snap).to_pandas()))  # → 1200
print(len(table.scan().to_pandas()))                         # → 1400

⚠️
Common stumble: preserve_index=False

Calling pa.Table.from_pandas(df) without preserve_index=False after .sample() silently adds a hidden __index_level_0__ column. Iceberg refuses the append with a schema-mismatch error. Always pass preserve_index=False.

05
What a Catalog Server Does

"Today's SqlCatalog is a local stand-in. A production catalog server does the same job — but for every tool across the whole company."

Apache Polaris, Unity Catalog, and AWS Glue are the production versions of exactly what SqlCatalog did today. They track which tables exist, their current metadata pointer, and who's allowed to read or write them.

⚡
Polaris ≠ Polars

Polars is the DataFrame library from Session 1 (written in Rust). Apache Polaris is a REST catalog server for Iceberg tables, built by Snowflake and donated to Apache — multi-engine, multi-cloud, shared across a whole organization. Similar name, completely different layer.

SituationLocal SqlCatalogShared catalog server (Polaris, Unity, Glue)
Who can see the table Only this laptop, this SQLite file Every tool across the company registered with the catalog
Where metadata lives A local SQLite file A managed service with its own access controls
Setup cost One line of Python, no network An infrastructure team provisions and runs it
Right fit for Learning, local prototyping, single-user analysis Multiple teams and engines sharing the same versioned tables
✅
The portable guarantee

Today's local setup and a production catalog server speak the exact same Iceberg table format underneath. The only thing that changes is who else gets to see the table. Nothing learned today has to be relearned on the job.

Check Your Understanding
1. A teammate says "Parquet is just a compressed CSV." What's the real distinction that matters for a data pipeline?
A. Parquet uses gzip compression by default while CSV never does, and that's the only real difference between them.
B. Parquet rows are stored in the exact order they were written, while CSV silently reorders them during compression.
C. Parquet files can only be read by Apache Spark, while a CSV file can be read by any tool.
D. Parquet stores data column-by-column with its schema and types embedded directly in the file, so readers don't have to re-infer types or scan columns they don't need.
2. Polars, DuckDB, and Arrow-backed pandas can all read the same Parquet file and hand data to each other with no conversion step. What makes that possible?
A. All three agree on Apache Arrow as their shared in-memory column format, so passing data between them needs no re-serialization.
B. Parquet files secretly contain a hidden Python pickle of the data that every one of these tools knows how to unpickle directly.
C. DuckDB silently converts every other tool's data into SQL text behind the scenes before handing it back.
D. Polars and pandas both quietly import DuckDB internally, so all three are actually the same engine wearing different names.
3. A table format like Iceberg sits on top of plain Parquet files. What problem does it solve that Parquet alone doesn't?
A. It makes the underlying files smaller by applying a second round of compression on top of Parquet.
B. It replaces SQL entirely with a brand-new query language built specifically for table formats.
C. It tracks which files belong to the table at each point in time, which is what makes atomic writes, schema evolution, and time travel possible across many Parquet files without rewriting them.
D. It requires every reader of the table to be written in the same programming language the table was originally created in.
4. After adding a new column to an existing Iceberg table with update_schema(), what happens to the rows that were already in the table?
A. The table silently refuses the schema change until every existing row is rewritten with a real value for the new column.
B. Existing rows simply show a null for the new column — nothing about them is rewritten or migrated.
C. The entire table is automatically dropped and has to be recreated from scratch with the new schema.
D. Every old row is duplicated once per existing column to preserve backward compatibility with old readers.
5. In an interview: "How would you let a BI dashboard, a Python notebook, and a Spark job all query the exact same versioned dataset without each one keeping its own copy?" What's the strongest answer?
A. Export the data as JSON once and have every tool parse the same JSON file independently.
B. Pick whichever one tool is most popular and force the other tools to call its API for every single query.
C. Keep three separate copies, one tuned for each tool, and write a nightly job to try to keep them all in sync.
D. Put the data in a table format like Iceberg on plain files — every engine that supports it reads the same underlying Parquet files and the same snapshot, with no copying and no sync job to maintain.
